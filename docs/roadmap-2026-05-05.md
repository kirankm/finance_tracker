# Roadmap: SMS to Trustworthy Ledger Through V1

Date: 2026-05-05

This roadmap plans the remaining V1 path in sprint-planning mode without expanding the current sprint scope. Sprint 6 remains focused on ledger promotion only.

## Planning Assumptions

- One sprint is roughly one week.
- Keep every sprint small enough to review, test, QA, and merge through CI.
- Continue using fake SMS fixtures only.
- Prioritize trust foundations before broad UI or analytics.
- Treat real SMS use as gated until authentication, backup, privacy, and fake-device forwarding validation are complete.
- Keep V2 ideas out of implementation until V1 is complete and explicitly re-planned.

## Week 1: Sprint 6 - Ledger Promotion

Goal: turn a reviewed, sufficiently mapped SMS candidate into a durable ledger transaction.

Primary outcomes:
- Reviewed fake SMS candidates can be promoted to `LedgerTransaction`.
- Unreviewed or insufficiently mapped candidates cannot enter the ledger.
- Promotion is traceable back to raw SMS, parser metadata, rules, and review metadata.
- Promotion is idempotent for the same raw SMS.
- Audit event is created for promotion.

Key risks to settle:
- Choose durable raw SMS to ledger linkage strategy.
- Decide whether minimal fake account seed behavior belongs in promotion or tests.

Exit criteria:
- Sprint 6 QA checklist complete.
- CI passes.
- Project status moves to planning Sprint 7.

## Week 2: Sprint 7 - Duplicate Detection

Goal: prevent duplicate SMS messages or repeated bank notifications from corrupting ledger totals.

Primary outcomes:
- Add duplicate detection for SMS-derived transaction candidates before or during promotion.
- Store duplicate decision metadata with explainability.
- Mark exact duplicates, likely duplicates, and unique candidates distinctly.
- Possible duplicates require review and do not affect ledger totals until resolved.
- Golden fixtures cover repeated message ids, repeated refs, same amount/date/merchant/account, and near duplicates.

Out of scope:
- Advanced fuzzy matching across long historical data.
- User-facing duplicate resolution UI beyond backend/API support.

Exit criteria:
- Duplicate rules are deterministic, tested, and auditable.
- Existing promotion path refuses or clearly handles duplicates.

## Week 3: Sprint 8 - Ledger Sanity Checks

Goal: make balance-impact assumptions visible before transactions are trusted for analysis.

Primary outcomes:
- Add ledger sanity checks using available balance when present.
- Store mismatch status and explanation metadata.
- Keep mismatched transactions reviewable instead of silently excluding or modifying them.
- Add fixtures for missing balance, matching balance, mismatch, credits, debits, and transfers.
- Update risk register for remaining balance limitations.

Out of scope:
- Full account reconciliation UI.
- Bank statement import.
- Automatic correction of mismatch causes.

Exit criteria:
- Ledger status is explainable for included, excluded, duplicate, and mismatch cases.
- Mismatch logic has focused unit and integration tests.

## Week 4: Sprint 9 - Corrections and Rule Learning Foundation

Goal: allow reviewed transactions to be corrected without losing history.

Primary outcomes:
- Add backend APIs to correct candidate or ledger fields such as merchant, category, purpose, account, amount, and date.
- Preserve before/after values in audit history.
- Make corrected data override deterministic rules without deleting original parser output.
- Define a rule-candidate shape for future user-approved rule creation.
- Add tests for correction priority, auditability, and rollback-resistant history.

Out of scope:
- Automatically creating production rules from corrections.
- LLM-generated rules.
- Rich UI forms, unless needed as a minimal QA surface.

Exit criteria:
- A wrong category or merchant can be corrected and explained later.
- Audit history clearly shows original parse, rule output, and user correction.

## Week 5: Sprint 10 - Minimal Review UI

Goal: provide a usable local web workflow for inspect, correct, review, and promote.

Primary outcomes:
- Add a minimal authenticated review queue screen.
- Show parsed fields, confidence, rule metadata, duplicate status, ledger status, and raw SMS detail only where appropriate.
- Support review, correction, and promotion actions against existing backend APIs.
- Keep UI dense and operational rather than marketing-oriented.
- Add frontend or HTTP-level tests appropriate to the stack.

Out of scope:
- Analysis dashboard.
- Insights screen.
- Mobile app.
- Polished account/category management.

Exit criteria:
- A fake SMS can be ingested, reviewed, corrected if needed, promoted, and verified from the UI.
- Raw SMS is not exposed in broad list views.

## Week 6: Sprint 11 - Import, Export, Backup, and Real-Use Readiness

Goal: reduce data-loss and privacy risk before relying on real personal data.

Primary outcomes:
- Add explicit export for ledger transactions, accounts, categories, and audit history.
- Add documented restore flow or improve existing backup workflow.
- Choose and document off-server backup storage.
- Run fake-device forwarding validation for the selected Android forwarder.
- Confirm shared-secret header support or plan a narrowly scoped tokenized fallback.
- Add operational checklist for first real SMS pilot.

Out of scope:
- Bank integrations.
- Native Android SMS reader.
- Automated cloud sync beyond the chosen backup target.

Exit criteria:
- Backup/restore/export path is documented and smoke-tested with fake data.
- Real SMS pilot has a concrete go/no-go checklist.
- Remaining production risks are recorded in the risk register.

## Week 7: Sprint 12 - Account and Category Management

Goal: make accounts, categories, and soft intent types editable enough to support real ledger use.

Primary outcomes:
- Add backend APIs and minimal UI for accounts.
- Add backend APIs and minimal UI for categories.
- Support category `intent_type` values for later analysis and insights.
- Preserve audit history for account and category changes that affect transactions.
- Prevent deleting or breaking accounts/categories that active transactions depend on.

Out of scope:
- Budgeting.
- Advanced net worth views.
- Investment holdings tracking.

Exit criteria:
- User can create and edit cash, bank, credit card, wallet, and investment-style account records.
- User can create and edit V1 categories without corrupting existing transactions.
- Existing SMS review and promotion flows use managed accounts/categories rather than hard-coded fake-only assumptions.

## Week 8: Sprint 13 - Manual Transaction Management

Goal: make manual transactions first-class and recoverable.

Primary outcomes:
- Add manual transaction create APIs and UI.
- Add edit, ignore, mark duplicate, soft delete, and restore flows.
- Support manual expense, income, cash spend, transfer-like records, refunds, and reversals where the current ledger model allows.
- Preserve correction and status-change history in audit events.
- Keep manual transactions clearly marked as `source: manual`.

Out of scope:
- Split transactions.
- Recurring commitments.
- Budget workflows.

Exit criteria:
- User can add, edit, ignore, delete, and restore a manual transaction without losing history.
- Manual entries participate in ledger totals and later search/analysis with clear source metadata.

## Week 9: Sprint 14 - Cash Tracking

Goal: make cash a proper account with explicit balance updates and cash spend handling.

Primary outcomes:
- Add cash balance update flow.
- Compare expected cash balance with user-reported cash balance.
- Offer a controlled way to record unexplained cash difference as uncategorized cash spend.
- Add audit events for balance updates and generated cash adjustment transactions.
- Include cash changes in ledger and analysis foundations.

Out of scope:
- Budgeting cash envelopes.
- Automatic cash inference from non-cash SMS.

Exit criteria:
- User can maintain a cash account balance and explain differences with auditable transactions.
- Cash transactions are searchable and analyzable alongside SMS and manual transactions.

## Week 10: Sprint 15 - Structured Search and Filters

Goal: make ledger data inspectable before building higher-level summaries.

Primary outcomes:
- Add structured search/filter API for ledger transactions.
- Add UI filters for date range, account, transaction type, purpose, category, merchant, amount range, review status, duplicate status, ledger status, and source.
- Add sortable transaction list with stable pagination or bounded result limits.
- Ensure deleted, ignored, duplicate, and ledger-excluded transactions are visible when explicitly filtered.

Out of scope:
- LLM chat search.
- Natural-language querying.
- Analysis dashboards.

Exit criteria:
- User can find and inspect any V1 transaction state through structured filters.
- Search results preserve audit/source context without exposing raw SMS broadly.

## Week 11: Sprint 16 - Analysis Screen

Goal: provide deterministic summaries of where money went.

Primary outcomes:
- Add monthly spend by category.
- Add spend by account.
- Add income vs expense views.
- Separate investments, savings, transfers, refunds, and reversals from normal expenses.
- Include cash balance changes and unmapped/review-needed counts.
- Add tests for analysis calculations using fake ledger fixtures.

Out of scope:
- LLM-written insights.
- Budget comparisons.
- Forecasting.

Exit criteria:
- Analysis totals are deterministic, explainable, and agree with ledger filters.
- Duplicate, ignored, deleted, and ledger-excluded transactions do not silently pollute analysis.

## Week 12: Sprint 17 - Insights Screen

Goal: surface important deterministic observations without relying on LLM authority.

Primary outcomes:
- Add insight generation from structured data.
- Highlight unmapped transactions, possible duplicates, ledger mismatches, cash mismatches, and notable category changes.
- Link each insight to the underlying transactions or ledger check.
- Allow insights to be dismissed or marked reviewed where useful.
- Keep any LLM-generated wording optional and non-authoritative if introduced at all.

Out of scope:
- LLM chat.
- Advanced anomaly detection.
- Budget recommendations.

Exit criteria:
- Insights are traceable to deterministic calculations.
- User can act on reviewable insights without losing source context.

## Week 13: Sprint 18 - User-Approved Rules

Goal: turn repeated corrections into explicit, user-approved rules.

Primary outcomes:
- Add rule candidate creation from user corrections.
- Add approve, reject, edit, disable, and audit flows for user-approved rules.
- Apply rule priority: user-approved rule, user correction, existing deterministic rule, LLM soft suggestion, unknown.
- Add golden dataset coverage for rule priority and non-regression behavior.

Out of scope:
- Natural-language rule creation.
- Fully automated LLM rule application.

Exit criteria:
- User can approve a rule from a correction and see it affect future fake SMS candidates.
- Rule application remains explainable and reversible.

## Week 14: Sprint 19 - Import and Export Completion

Goal: finish V1 import/export and make data portability explicit.

Primary outcomes:
- Export ledger transactions to CSV.
- Export ledger, accounts, categories, audit history, raw SMS metadata, and rules to JSON.
- Add import/restore validation for exported JSON.
- Keep raw SMS body handling explicit and privacy-conscious.
- Document supported export format versions.

Out of scope:
- Bank statement import.
- Third-party sync.

Exit criteria:
- User can export useful CSV for external analysis.
- User can export and validate a complete JSON backup with fake data.

## Week 15: Sprint 20 - Production Pilot Hardening

Goal: make the app safe enough for a small real-SMS pilot.

Primary outcomes:
- Complete fake-device SMS forwarder validation.
- Confirm auth strategy for production forwarding, including header support or a scoped fallback.
- Add operational checks for HTTPS, app port exposure, secrets, backups, and logs.
- Review raw SMS exposure across APIs and UI.
- Run backup/restore smoke test against fake production-like data.
- Create first-real-use checklist and rollback plan.

Out of scope:
- Scaling beyond personal use.
- Multi-user authentication.
- Native Android SMS reader unless the forwarder path fails.

Exit criteria:
- Real-SMS pilot has a written go/no-go checklist.
- Known unresolved risks are explicit in the risk register.
- No real data is committed or used in tests.

## Week 16: Sprint 21 - V1 Stabilization and Release Candidate

Goal: stabilize the full V1 workflow and decide whether V2 planning can start.

Primary outcomes:
- Run end-to-end fake-data regression across ingest, parse, enrich, review, correct, promote, duplicate handling, ledger checks, search, analysis, insights, export, backup, and restore.
- Fix high-priority correctness, privacy, auditability, and migration issues.
- Update docs, decisions, risk register, and backlog.
- Define V1 release notes and residual limitations.
- Decide whether real pilot feedback requires another V1 hardening sprint before V2.

Out of scope:
- Starting V2 implementation.
- Adding new V2 features during stabilization.

Exit criteria:
- V1 release candidate is documented.
- CI and local Docker checks pass.
- QA checklist covers the full fake-data workflow.
- V2 planning can begin only if no blocking V1 trust risks remain.

## V2 Planning Boundary

Do not implement these in V1. Re-plan them after the V1 release candidate:

- Bank integrations.
- LLM chat interface such as "Ask my money".
- Split transactions.
- Recurring commitments and recurring pattern detection.
- Budgeting.
- Investment holdings tracking.
- Advanced net worth dashboard.
- Natural-language rule creation.
- Advanced anomaly detection.
- Native Android SMS-reading app, unless external forwarding fails and the project explicitly changes direction.

## Dependencies and Ordering

The order matters:

1. Ledger promotion creates the durable record that later checks protect.
2. Duplicate detection should land before meaningful analysis.
3. Ledger sanity checks should land before trusting balances or summaries.
4. Corrections must preserve explainability before broadening user workflows.
5. UI should use stable backend contracts rather than inventing them.
6. Account/category/manual/cash workflows should land before broad analysis so summaries use real user-editable data.
7. Search should land before analysis and insights so every aggregate can be inspected.
8. Real-use readiness should wait until backup, privacy, and forwarder risks are handled.
9. V2 planning starts only after the V1 release candidate is stable.

## Deliberately Deferred

- Analysis and insights screens should wait until duplicate, ledger sanity, search, and user-editable transaction data exist.
- LLM suggestions should wait until user correction and rule approval flows exist, and must remain non-authoritative.
- Native Android SMS reading remains later unless the external forwarder path fails validation.
- Budgeting, investments dashboard, bank integrations, and chat remain out of V1.
